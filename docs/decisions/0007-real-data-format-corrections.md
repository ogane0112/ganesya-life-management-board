# 0007. 実データに基づくパーサー修正

- ステータス: 採用
- 日付: 2026-08-16

## コンテキスト

[decisions/0002](./0002-status-calculation-approach.md) の時点では
`ogane0112/life-management` の実際の中身を見られず、ファイル命名規則・
Markdown形式を仮定してパーサーを実装していた。デプロイ後、実際の画面で
全ステータスが0/100になる現象が報告されたため、`life-management` を
このセッションに接続し（ユーザーの明示的な許可のもと）実際のファイル構成を
確認した。

## 判明した実際の形式

- `logs/` … 想定通り `YYYY-MM-DD` 始まりのファイル名（一致、変更不要）
- `finance/`, `home/`, `decisions/` … ファイル名に日付は**入っていない**。
  代わりに全ファイルがYAML frontmatterを持ち、`last_updated: "YYYY-MM-DD"`
  （なければ `created`）という統一フィールドで更新日を記録している
- `chat-summaries/` … frontmatterなし。日付は使わない設計のため実害なし
- `profile/qualifications.md` … 想定した英語ヘッダーの単一テーブルではなく、
  「学歴」「取得済み資格・免許」「勉強中・取得予定」という3つの日本語見出し
  ＋テーブルが1ファイルに同居。有効期限は空欄ではなく `無期限` という文字列
- `profile/career.md` … 「現職」セクションは項目名/内容の**key-valueテーブル**
  （1行1フィールド）、「職歴」セクションは `期間`（例: `2020-04 - 2023-03`）
  を持つ通常テーブル。想定した「title/date」形式の単純なイベント一覧ではない

## 決定

`packages/worker/src/parsers.ts` を実際の形式に合わせて全面的に書き直した。

1. **frontmatter日付の読み取り**（`packages/worker/src/frontmatter.ts` 新規）:
   `last_updated`/`created` をYAMLパーサーなしで正規表現抽出。
2. **セクション抽出**（`markdown-table.ts` に `extractSection` を追加）:
   見出し単位で本文を切り出してから `parseMarkdownTable` に渡すことで、
   1ファイル内の複数テーブルを混同しないようにした。
3. **key-valueテーブルの反転**（`tableToKeyValue` を追加）: 「現職」のような
   項目/内容形式のテーブルをオブジェクトルックアップに変換。
4. **qualifications.md**: 「取得済み資格・免許」セクションのみを対象にし、
   「学歴」「勉強中」は対象外とした（要件の「資格数」は取得済みのものを
   指すと解釈）。`無期限`/`-`/空欄を「失効しない」として扱う。
5. **career.md**: 「現職」の入社日と「職歴」の期間開始日の両方からイベントを
   構築するようにした。ただし現時点の実データはどちらも `-`（未記入）の
   ため、LV計算は当面 xp=0 → Lv.1 のままになる（バグではなく実データ不足）。
6. **finance/ の鮮度判定**: ファイル名日付が取れない場合、
   `GitHubClient.listDirectory` に `resolveDatesFromContent` オプションを
   追加し、該当ファイルのみ内容を取得してfrontmatter日付を読む
   （全カテゴリに適用すると追加API呼び出しが増えすぎるため、日付が
   実際に必要な `finance/` のみに限定）。

## 検証

`/workspace/life-management` の実クローンに対して抽出ロジックを手動実行し
（`packages/worker/test/parsers.test.ts` 等の自動テストとは別に、実データでの
サニティチェックとして）、意味のある値が得られることを確認した
（2026-08-16時点、日付は前後する）:

- HP 18（直近30日のログ12件、streak 0）
- INT 69（取得済み資格3件、いずれも無期限で有効）
- 財力 58（financeファイル2件、いずれも90日以内更新）
- 装備 20（homeファイル2件）
- 判断力 47（decisionsファイル9件）
- 絆 38（chat-summariesファイル12件）
- LV 1（career.mdに実データがまだ入っていないため）

## 残課題

- `career.md` の「現職」「職歴」に実データ（入社日など）が入力されれば
  LVは自動的に反映されるようになる。パーサー側の対応は完了しているため、
  ユーザー側でのデータ入力待ち。
- デプロイ済みWorkerで確認された「全カテゴリが0」という結果は、
  件数のみに基づく装備・判断力・絆まで0だったことから、本コミットで
  修正したパース形式の問題だけでは説明がつかない。GitHub PATの
  権限不足など、Worker側のデータ取得自体が失敗している可能性が高く、
  これは本セッションからは検証・修正できない
  （[deployment.md](../deployment.md) のトラブルシューティング参照）。
