# 0002. ステータス算出式の設計方針

- ステータス: 採用（要再検証）
- 日付: 2026-08-15

## コンテキスト

要件定義書は算出ロジックを「案」として提示するのみで、「具体的な計算式・重み付けは
実装フェーズで詰める」と明記されていた。かつ、このセッションからは実際の
`ogane0112/life-management`（private）リポジトリの中身を参照できない
（本セッションのGitHubアクセス範囲は `ogane0112/ganesya-life-management-board` のみ）。

## 決定

1. GitHub APIレスポンス形状に依存しない `RepoSnapshot` という中間データ契約を定義し、
   計算ロジック（`stats-engine`）を実データ形式非依存にした。
2. 件数ベースの指標には「飽和スコア」（`saturatingScore`、詳細は
   [design/status-calculation.md](../design/status-calculation.md)）を採用し、
   無限成長・0除算を避けた。
3. ファイル名の先頭に `YYYY-MM-DD` が付く命名規則、`qualifications.md`/`career.md` が
   Markdownテーブル形式であることを**仮の前提**として明文化し、パーサーをその前提の上に
   実装した。

## 検討した代替案

- **YAMLフロントマター形式でのプロフィールファイルパース**: より構造化できるが、
  `js-yaml` 等の追加依存が必要になり、Worker側のバンドルサイズが増える。テキスト量の少ない
  個人リポジトリ用途にはMarkdownテーブル＋自前パーサーで十分と判断し見送り。
- **ファイルコミット日時をGitHub Commits APIで取得**: より正確な「最終更新日」が取れるが、
  ディレクトリ内ファイル数だけAPI呼び出しが増え、GitHub APIのレート制限に対して非効率。
  ファイル名からの日付抽出で代替し、パース失敗時は「日付不明」として安全側にフォールバック
  する設計にした。

## 結果・影響

- 実データを見ずに計算式を確定させたため、**実リポジトリ投入後の検証が必須**。
  具体的には: ①ファイル命名規則が前提と一致するか、②現実の記録頻度に対してHP/財力等の
  スコアが体感的に妥当な速度で伸びるか、の2点を要確認。
- 重み・半減点は `packages/stats-engine/src/calculate.ts` の `STATUS_WEIGHTS` に一元化して
  あるため、実データに合わせた調整は1ファイルの定数変更で完結する。
- この前提のズレは各所（`packages/worker/src/github.ts`, `parsers.ts`）にコメントとして
  明記し、コードを読むだけでも「仮決め」であることが分かるようにした。
